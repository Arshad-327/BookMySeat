# BookMySeat — Project Rules

This file is the single source of project rules. Do not copy it into AGENTS.md or any other file — a copy drifts the moment this one changes.

This file is the project constitution. Follow it for every task in this repo, and re-read it whenever you are unsure.

## What this project is

A distributed event ticketing platform. The central engineering problem: **two users must never be able to book the same seat concurrently.** Seats are held temporarily for 10 minutes in Redis before payment. Everything else exists to serve that problem.

## Non-negotiable technical decisions

- Java 21, Spring Boot 3.3.x, Maven multi-module monorepo
- Services: `api-gateway` (Spring Cloud Gateway, reactive), `auth-service`, `event-service`, `booking-service`, `notification-service`
- `payment-service` is OPTIONAL. Do not create it unless I explicitly ask.
- MySQL 8, database per service. No cross-schema foreign keys. No service reads another service's tables.
- Redis 7 for seat holds, idempotency keys, rate-limit counters
- Kafka in KRaft mode. Exactly one topic: `booking.confirmed`, published via transactional outbox
- Flyway for all schema changes. `ddl-auto` is always `validate`, never `update` or `create`
- springdoc-openapi for Swagger
- Lombok for boilerplate only
- Frontend: React 18, Vite, TypeScript, React Router 6, Tailwind, Axios, TanStack Query, React Context. TypeScript rather than JavaScript because the API contract was designed field by field, nullability included, and the response shapes deserve types that break the build when they drift. Lives in `frontend/`, outside the Maven reactor, and talks to the gateway on 8080 only

## Timekeeping

The development host is not UTC and the containers are. One policy, project-wide, no exceptions.

- Every instant in Java is `java.time.Instant`. Never `LocalDateTime`. This covers entities, DTOs, error-response timestamps and test fixtures, not just expiry fields
- Every timestamp column is MySQL `TIMESTAMP(6)`. Never `DATETIME`, and never a bare `TIMESTAMP`. The `(6)` is mandatory and applies to *every* timestamp column without exception — expiry fields and bookkeeping columns like `created_at` alike. It is not decoration on two counts. First, precision: a bare `TIMESTAMP` is second-precision and MySQL *rounds* a fractional value on insert, which would move a seat hold's expiry by up to half a second. Second, fidelity: `(6)` is microsecond precision, which is what `java.time.Instant` round-trips through the JDBC driver, so an `Instant` written and read back is the same value rather than a truncated one. The columns already built prove the standard — `auth_db.users.created_at`, `auth_db.refresh_tokens.expires_at`, `event_db.shows.starts_at` are all `timestamp(6)` in the live database. A migration writing anything else is wrong, not a variation
- Every `Instant` written from Java to a `TIMESTAMP(6)` column is truncated to microseconds **at assignment**: `.truncatedTo(ChronoUnit.MICROS)`. An `Instant` carries nanoseconds and the column cannot, and MySQL does not cut the excess off, it ROUNDS it - so an untruncated write stores a value that is not even a prefix of the one in memory (`…123456789Z` is kept as `…123457`). Truncating first makes that rounding a no-op, so the value a response serialises from memory and the value a later read returns are the same. No exceptions for "nobody reads it back": that was true of `bookings.expires_at` until a frontend needed a countdown, and a rule with an exception list has to be re-derived at every new write site. Fix it at the write, never in the serialiser or the column - that is the only version where the two cannot disagree. Guarded by `HoldExpiryRoundTripMySqlTest` in booking-service, which pins a clock with nine fractional digits. Database-written columns (`DEFAULT CURRENT_TIMESTAMP(6)`) are already microseconds and need nothing
- Every JDBC URL pins `connectionTimeZone=UTC&preserveInstants=true`
- The MySQL container runs with `--default-time-zone=+00:00`. `+00:00`, not `UTC`: named zones need the timezone tables loaded and the `mysql:8` image does not load them
- No query uses SQL `NOW()` or `CURRENT_TIMESTAMP` for comparison LOGIC. Any "is this expired" query takes an explicit `:now` parameter supplied as `Instant.now(clock)` from the injected `Clock`. `DEFAULT CURRENT_TIMESTAMP(6)` on insert stays — that is bookkeeping, not logic
- Every service has a `ClockConfig` returning `Clock.systemUTC()`. Every time-based decision reads through the injected `Clock`, never through a bare `Instant.now()`, so tests can pin it
- Known limit: MySQL `TIMESTAMP` cannot hold a value past 2038-01-19T03:14:07Z. Nothing here schedules that far out. If that ever changes it is a deliberate decision, not a silent truncation

## Forbidden — do not add these, do not suggest them

Eureka or any service discovery, Resilience4j, MapStruct, Zustand, Redux, Kubernetes, Elasticsearch, GraphQL, any real payment gateway, any AI or ML feature, any additional microservice, any component library.

Services find each other by Docker Compose service name, e.g. `http://event-service:8082`

## Coding rules

- Never add a Maven or npm dependency that is not already present without asking me first and explaining why
- Never modify files outside the module I named in my request
- DTO mapping is hand-written static methods
- Every endpoint returns a DTO, never a JPA entity
- Constructor injection only. No field `@Autowired`
- Package layout per service: `config`, `controller`, `dto/request`, `dto/response`, `dto/event`, `entity`, `repository`, `service`, `client`, `scheduler`, `exception`, `mapper`. `dto/event` holds outbound message payloads (Kafka), which are neither requests nor responses

## How I want you to work

- For any task touching more than 3 files, show me a plan and wait for approval before writing code
- After writing code, give me the exact commands to verify it works
- If my prompt contradicts this file, stop and ask. Do not guess
- NEVER invent test results, benchmark numbers, timings, or performance figures. If a number is needed, tell me which command to run and wait for me to paste the real output
- Keep changes small. Several small commits beat one large one

## Current status

Week 5 closed, and week 6's first piece - Docker Compose - is done. The backend is feature-complete: the seat-contention core is built and measured, the gateway routes, rate-limits and authenticates, and a confirmed booking reaches an email through a transactional outbox, Kafka and notification-service. The frontend covers the whole booking journey. `docker compose up -d --build --wait` runs all of it from a clone. There is still no CI and no README: tests, the smoke script and the port check are all run by hand.

**Built**

- Infra: `docker-compose.infra.yml` runs MySQL 8.4, Redis 7, Kafka (KRaft, topic auto-creation off) and MailHog, published on loopback. It is the whole run-from-the-IDE workflow by itself, and it is INCLUDED by `docker-compose.yml` rather than copied, so the infrastructure is defined once. Every service has a `default` (localhost) and a `docker` (service name) profile
- `auth-service` (8081): register, login, refresh with rotation, logout, `GET /me`. Issues JWTs. Internal `GET /api/internal/users/{id}` returns id, email and name only, for notification-service; it answers 404 for an unknown id where `/me` answers 401, and the difference is load-bearing downstream
- `event-service` (8082): public events list/detail and show seat map; admin venues, seat generation, events and shows behind `X-User-Role: ADMIN`; internal `POST /api/internal/shows/{id}/seats/book` with `@Version` optimistic locking (layer 2) and internal `GET /api/internal/shows/{id}?seatIds=` , a narrow read model (title, venue, start, seat labels) shaped for one confirmation email. `demo` profile seeds data. The seat map carries `eventId`, `eventTitle`, `venueName` and `startsAt`, so a show page needs no second call and there is no `GET /api/shows/{id}`. `GET /api/events` lists ONLY events with an upcoming show (an EXISTS predicate, applied to the count too) and each card carries `nextShowStartsAt` and `fromPrice`; both are never null because of that filter. Seeded shows start at 18:30 Asia/Kolkata, computed from the zone
- `booking-service` (8083): `POST /api/bookings/hold` (Redis Lua holds, layer 1; Idempotency-Key required, Redis fast path in front of a unique index), `POST /{id}/confirm` (layer 3 unique `sold_show_seat_id`), `DELETE /{id}` cancel with immediate hold release, `GET /{id}`, `GET` mine (paged: default 20, cap 100, newest first, repeatable `status`, no default filter). `ExpiredBookingSweeper` every 60s. Confirm, cancel and sweep lock the booking row. Confirm writes a thin `BookingConfirmedEvent` (ids only, no personal data) to the `outbox` table (V3) in the same transaction via `OutboxWriter` (`Propagation.MANDATORY`); `OutboxPublisher` sends it to `booking.confirmed` (one partition, declared in `KafkaConfig`) every 2s, at least once, stopping at the first failure. Both scheduled jobs are single-instance and share a 2-thread scheduler. A booking carries what it is for - `eventId`, `eventTitle`, `venueName`, `showStartsAt`, and `rowLabel`/`seatNumber` per seat - copied onto the row at hold time (V4) from the seat map hold already fetches, never re-read; null on bookings held before V4. Seats are stored and returned in venue order
- `api-gateway` (8080, WebFlux): routes `/api/auth/**`, `/api/events/**`, `/api/shows/**`, `/api/admin/**` and `/api/bookings/**` from `application.yml`, with central CORS. `/api/internal/**` and `/actuator/**` are deliberately unrouted (404), and a test enforces it. Its own health is on management port 8090. `JwtAuthenticationFilter` (order -100) strips every inbound `X-User-*` header in any case, lets `/api/auth/**` and GET catalogue reads through with no token, and requires a valid HS256 access token everywhere else, injecting `X-User-Id` and `X-User-Role` from it. Errors use the standard shape with an `Instant` timestamp. jjwt's version is managed in the root pom, shared with auth-service. `RateLimitFilter` (order -200, before JWT) is a reactive token bucket per client IP per route policy, ported from github.com/Arshad-327/rate-limiter with its Lua script byte-for-byte (SHA-1 pinned by a test): default burst 40 / 2 per second, `/api/demo/**` burst 20 / 1 per 3 seconds. It fails open with a short Redis timeout; `GET /api/demo/spam` (a `no://op` route) exists to demonstrate a 429 Services stay directly reachable on 8081-8083, where `X-User-Id` is still taken on trust. A downstream that refuses the connection is 503 (it was 500); one that accepts and never answers is 504, from Spring Cloud Gateway's own response timeout, and is deliberately left distinct
- `notification-service` (8085): consumes `booking.confirmed` (group `notification-service`, `auto-offset-reset: earliest`, concurrency 1) and sends the confirmation through Spring Mail to MailHog. **No inbound HTTP at all** beyond actuator health, enforced by `NoHttpSurfaceTest`; no database. Dedupe is one Redis key per `eventId` with a 24h TTL, and the order is **check, SEND, mark** — a crash between marking and sending loses an email, between sending and marking duplicates one, and the duplicate is the better failure. auth-service is REQUIRED (transient failures retried forever with a 30s-capped backoff; 404 and 401/403 are permanent, logged with distinct messages and committed past so one deleted user cannot block the partition); event-service is BEST-EFFORT (any failure sends the email with ids instead of names). Show times render in Asia/Kolkata. Design and evidence in `docs/notification-design.md`
- Load tests: k6 single-seat contention (50 requests → 1 claim, down from 10 unprotected) and overlapping-seats all-or-nothing, with an independent verifier. Results in `docs/load-test-results.md`, design in `docs/concurrency-design.md`
- `scripts/e2e-smoke.sh`: the regression net for weeks 5 and 6. 13 steps, one PASS line each, exiting non-zero on the first unexpected response and naming the step and what it actually got. Everything goes through the gateway on 8080 — a step that used 8081-8083 would stay green after the gateway stopped doing its job — except reset-fixtures.sh and MailHog's API, which are not platform traffic. It seeds through `load-tests/reset-fixtures.sh`, not the admin API: registration creates a USER and nothing mints an ADMIN, so `/api/admin/**` is unreachable from the script by design, and the truncate-and-reseed makes the show and seat ids identical on every run. Covers: the public seat map with no token; hold; Idempotency-Key replay returning the same booking id and no second row; a second user refused with the conflicting seat id named; confirm; the seat map turning BOOKED; the confirmation email in MailHog, subject and seat labels decoded from RFC 2047 and quoted-printable before comparing; cancel releasing the holds at once; 401 with no token; a spoofed `X-User-Id` ignored; `/api/internal/**` unrouted. It spends **17 of the rate limiter's 40-token burst**, listed per step in the file header and printed again at the end — a later step that pushes it toward 40 has hit a real constraint, not a flake. Two steps deliberately do not assert what they appear to, and say so: step 10 re-holds the cancelled seats rather than re-reading the map, because a held seat reads AVAILABLE there by design and the map would pass with the release deleted; step 12 asserts on the returned `userId` and never the status code, because the response is 201 whether or not the gateway stripped the header
- Tests: 246 backend across gateway (58), auth (26), event (69), booking (80) and notification (13), on real MySQL, Redis and Kafka via Testcontainers where it matters; zero skipped, no `@Disabled`. 88 frontend (`npm test`, vitest, plain Node) on the pure modules only - seat selection, checkout decisions, error classification - each shown to fail against a deliberately broken source
- Frontend (`frontend/`, React 18, TypeScript, Vite): browse, event page, seat map (polled every 5s, ARIA grid with one tab stop), selection and hold, checkout (countdown, confirm, cancel) and My Bookings (three tabs, each sending `status`). Talks to the gateway on 8080 only, cross-origin, no proxy. Access token in memory, refresh token in localStorage; one interceptor, single-flight refresh. The rules that can be wrong are plain functions in `src/lib/seatSelection.ts` and `src/lib/checkout.ts`. Pages were verified by driving headless Chrome by hand, which is not repeatable from a checkout
- Docker: one `docker/Dockerfile.service` for all five services (module and port as build args, `~/.m2` as a shared BuildKit cache mount) and `frontend/Dockerfile` (a built bundle behind nginx). `docker-compose.yml` publishes 8080 and 5173 on loopback and NOTHING for 8081-8083, 8085 or 8090; `scripts/check-compose-ports.sh` fails, naming the port, if that ever changes. event-service runs with the `demo` profile, so an empty volume is seeded once and a restart is a no-op. Measured: a first build from an empty cache 304 s, a restart 32 s, about 2.3 GB of memory across the ten containers

**Not built**

- A second, per-user rate-limit tier after JWT validation (only the per-IP, pre-auth tier exists)
- No cleanup of published outbox rows
- No pruning of `auth_db.refresh_tokens`. Rotation and logout mark rows revoked and `deleteByUserId` exists, but nothing removes revoked or expired rows on a schedule, so the table grows the same way the outbox does. Same shape of gap, same absent job
- No CI. Nothing runs `mvn test`, `npm test`, `scripts/check-compose-ports.sh` or `scripts/e2e-smoke.sh` automatically; all are run by hand. The smoke test needs the stack up and, for its fixture reset, Java and a built event-service jar on the host
- No README, and no deployment. A live URL was decided against: the README, three screenshots in `docs/images/` and the one-command local run are the deliverable
- The rate limiter keys on client IP, and inside Docker every browser on the host reaches the gateway from the bridge address, so the compose demo exercises ONE bucket. It does not show two users with separate budgets
- No component or browser tests for the frontend. Unit tests cover its pure logic only; everything about the pages themselves was checked by hand in headless Chrome and would have to be checked by hand again
- Two browser tabs can race on the rotating refresh token. The refresh is single-flight within one page (`frontend/src/api/http.ts`), but each tab has its own copy of that promise and they share one refresh token in localStorage; if both refresh in the same instant, one presents a token the other has just revoked and is signed out. Accepted and documented there, not coordinated - the cost is a re-login in one tab
- booking-service started while Kafka is down never creates `booking.confirmed`. The topic is declared once, at startup; with the broker absent the service starts, logs "Could not create admin" and does not try again, and auto-creation is off. Measured: the topic was still missing two minutes after Kafka came up, a confirm then succeeded and its outbox row sat unpublished, and a restart of booking-service created the topic and delivered the email. Nothing is lost - the outbox holds the event - but "survives Kafka being down" is true of requests, not of that one startup step. `docker-compose.yml` avoids it by waiting for Kafka to be healthy
- No dead-letter topic. A permanently undeliverable notification is logged and dropped; constrained by the one-topic rule, not overlooked
- The browse list (`GET /api/events`) cannot be sorted by next show date. `nextShowStartsAt` comes from a second statement that runs after the page query, and sorting applies to Event properties in the first, so `?sort=nextShowStartsAt` is a 400 and "soonest first" does not exist
- Admin writes are create-only: venues, seat generation, events and shows can be created and never updated or deleted. Fine until an admin UI needs to correct a typo. **Show-update has a dependency outside event-service:** `booking_db.bookings.show_starts_at` is a copy of the show's start time made at hold time, correct only because a show cannot be rescheduled. Whoever builds show-update must also correct that column for every existing booking of the show, and there is no channel to do it with today (one topic, flowing the other way; no cross-schema reads). The copied title, venue and seat labels are deliberate snapshots and must NOT be synced
- api-gateway has no springdoc and there is no aggregated API page across services. The three services with an HTTP surface each have their own `OpenApiConfig`; notification-service has no HTTP surface and needs none

# P4.9 Backend review — findings

*A review of the backend at commit `b1d1aa7`, carried out on 2026-09-18, before the frontend exists. Medium depth. Report only — no code was changed in the pass that produced it.*

## Tier 1 — would fail in a demo, or already fails silently

### 1. A confirm that times out leaves the seat permanently unsellable and locks its own owner out
`booking-service/src/main/java/com/bookmyseat/booking/service/BookingService.java:238-244`, `client/EventClient.java:93-106`

`confirm()` flushes the local transaction (line 238), then calls event-service (line 244), then commits. event-service's `markBooked` is `@Transactional` and commits on method return, *before* its response is written. booking-service's read timeout is 5s (`app.event-service.read-timeout`).

Interleaving, no crash required:

1. User confirms booking 5, seats `[9001]`. Lock taken, PENDING, hold valid, flush OK, outbox row written.
2. `POST /api/internal/shows/301/seats/book` reaches event-service. It commits `UPDATE show_seats SET status='BOOKED', version=1 WHERE id=9001`.
3. event-service is slow to write the response — a GC pause, a busy connection pool, 5.1s total. booking-service's read timeout fires.
4. `RestClientException` → `EventServiceUnavailableException` (EventClient.java:103) → booking-service rolls back. Booking 5 is still PENDING, the outbox row is gone, the user gets 503.
5. User retries within the 10-minute window. Booking is PENDING, `expiresAt` is still in the future, the Redis hold is still theirs (the release only runs `afterCommit`, so it never ran). Everything passes — until `markSeatsBooked`, where event-service answers **409 seat already BOOKED**.

Outcome: seat 9001 is `BOOKED` in `event_db` forever, no booking anywhere is CONFIRMED for it, no email was sent, and the one user who could legitimately claim it now gets 409 on every retry until the hold lapses. After the sweeper marks the booking EXPIRED, the seat reads BOOKED on the seat map and can never be sold.

The three layers are all satisfied here. They prevent a seat being sold *twice*; nothing prevents it being sold *zero* times and marked sold. `EventClient.java:89-91` acknowledges the gap in a javadoc — but it is not in CLAUDE.md's "Not built" list, and it is reachable from a slow response rather than only from a crash. This is the one finding I would fix before anything else.

### 2. Reusing the hold's `Idempotency-Key` on confirm returns 200 without confirming anything
`booking-service/src/main/java/com/bookmyseat/booking/service/IdempotentBookingService.java:149-157`, `controller/BookingController.java:237-238`

`confirm` consults the *same* Redis namespace that `hold` writes to (`idem:{key} -> bookingId`), and on a hit returns the cached booking immediately — without calling `bookingService.confirm`, and without ever looking at the `{id}` path variable.

Scenario:

1. `POST /api/bookings/hold` with `Idempotency-Key: K` → booking 5, PENDING. `IdempotencyService.record` writes `idem:K -> 5`.
2. The client reuses `K` on `POST /api/bookings/5/confirm`.
3. `fromCache` hits `idem:K -> 5`, ownership passes, and the controller returns **200 with `{"id":5,"status":"PENDING"}`**.
4. Nothing was confirmed. The seat is never marked BOOKED, no outbox row, no email. Ten minutes later the sweeper expires the booking and the user's seat quietly evaporates.

A React app that generates one idempotency key per checkout flow and attaches it to both calls — the obvious implementation — hits this every single time. The response is a 200 with a booking body, so the frontend has no signal that anything went wrong except that `status` isn't `CONFIRMED`.

A second, related consequence: on a cache hit the path variable is ignored entirely, so `POST /api/bookings/99/confirm` with a key resolving to booking 5 returns booking 5. There is no cross-user leak (`checkOwnership` at IdempotentBookingService.java:174 catches that with a 409), but the wrong object is returned for the requested id.

## Tier 2 — security and load

### 3. Nothing stops a booking for a show that has already started
`booking-service/src/main/java/com/bookmyseat/booking/service/BookingService.java:101`, whole confirm path

Grep for `startsAt` across `booking-service/src/main/java` returns nothing. `hold` fetches the seat map for price and availability and never reads the show's start time; `confirm` doesn't either. `GET /api/events/{id}` filters `upcomingShows` by `startsAt >= :now` (`ShowRepository.findUpcomingByEventId`), so the catalogue hides past shows — but that is a display filter, not a rule.

`POST /api/bookings/hold {"showId": <a show that started last week>, "seatIds":[...]}` → 201, then confirm → 200 CONFIRMED, plus a confirmation email for a concert that already happened. Show ids are sequential and the seat map for a past show is public and unauthenticated, so the ids are trivially discoverable. This is the first thing I'd expect an interviewer to try.

### 4. auth-service answers 500 where it should answer 400 and 409
`auth-service/src/main/java/com/bookmyseat/auth/exception/GlobalExceptionHandler.java:65`, `service/AuthService.java:40-53`

The advice handles `DuplicateEmailException`, `InvalidCredentials`, `InvalidRefreshToken`, `UserNotFound`, `MethodArgumentNotValid`, and then `Exception.class`. It does not extend `ResponseEntityExceptionHandler` and has no handler for `HttpMessageNotReadableException` or `DataIntegrityViolationException`. `ExceptionHandlerExceptionResolver` runs ahead of `DefaultHandlerExceptionResolver`, so the catch-all wins. Two concrete cases:

- `POST /api/auth/login` with body `{"email":` → `HttpMessageNotReadableException` → **500 "An unexpected error occurred"**. booking-service and event-service both map this to 400 (`booking .../GlobalExceptionHandler.java:185`, `event .../GlobalExceptionHandler.java:133`). auth-service is the odd one out, and it's the service the frontend hits first.
- Two `POST /api/auth/register` with the same email arriving concurrently: both pass `existsByEmail` (line 40) before either commits, the loser's `saveAndFlush` (line 53) trips the `UNIQUE` on `users.email` → `DataIntegrityViolationException` → **500**, not the 409 the check-then-insert was written to produce. A double-clicked Sign Up button reproduces it.

### 5. The confirm transaction holds a pooled connection and a row lock across an HTTP call, with no pool sizing anywhere
`booking-service/src/main/java/com/bookmyseat/booking/service/BookingService.java:187-250`; no `spring.datasource.hikari.*` in any `application.yml`

`findByIdForUpdate` takes a connection and a `SELECT ... FOR UPDATE`, and holds both across `eventClient.markSeatsBooked` — up to 2s connect + 5s read. Hikari's default `maximumPoolSize` is 10 and `connectionTimeout` is 30s, neither overridden.

The repository javadoc defends the *lock* (one user per booking row, machine time not human time) and that argument is sound. It does not address the *connection*: 10 concurrent confirms for ten different bookings by ten different users saturate the pool while every one of them is blocked on the network. The 11th request waits up to 30s and then fails with a pool-timeout 500 — not a 503, and not attributable to event-service in the log. The k6 suite only contends on `/hold`, so this has never been exercised.

### 6. Every `/hold` transfers the entire seat map over HTTP
`booking-service/src/main/java/com/bookmyseat/booking/client/EventClient.java:39-48`, called at `BookingService.java:101`

`fetchSeatsById` has no "give me these two seats" path, so it fetches every seat in the show and indexes it in memory, on the hot path, to read two prices. At the demo's 60 seats this is invisible. `GenerateSeatsRequest` permits 200 rows × 500 seats = 100,000 seats, and `GET /api/shows/{id}/seats` is unpaginated (`ShowController.java:81`), so a real arena makes every hold a 100k-row JSON fetch and parse — and the single-seat contention test's 50 concurrent holds become 50 of them. Flagged in the code as "worth revisiting"; at the sizes the validators allow, it's the dominant cost of a hold.

## Tier 3 — the frontend will trip over these

### 7. There is no endpoint that lets the UI render a seat-map page or a bookings list
Three gaps that compound:

- `SeatMapResponse` (`event-service/.../dto/response/SeatMapResponse.java`) carries `showId`, counts and rows. No event title, no venue, no `startsAt`.
- There is no `GET /api/shows/{id}` — `ShowController` only exposes `/{id}/seats` (line 81). So from the URL `/shows/301` the frontend cannot discover the event id, let alone the title.
- `BookingResponse.seats` is `[{showSeatId, price}]` (`BookingSeatResponse`). No row label, no seat number, no show title, no start time.

So a deep link or a page refresh on the seat-map route renders a grid with no header, and "My Bookings" renders `Booking #12 — seat 9001, 9002`. The data exists — `GET /api/internal/shows/{id}?seatIds=` returns exactly the title, venue, start time and seat labels needed — but it is deliberately unrouted, and correctly so. The frontend needs either a public projection of that endpoint or those fields folded into the two existing responses. Worth deciding before week 5 starts, not during.

### 8. Held seats read `AVAILABLE`, so the click-to-409 rate will be the visible failure mode
`event-service/.../dto/response/SeatResponse.java`, `ShowController.java:81`

Documented and deliberate (no `HELD` status in the database), and the smoke test's step 10 note shows it's understood. Stating it here only because it's the frontend's problem now: the UI will show a seat as free, the user clicks, and `POST /hold` returns 409 with `conflictingSeatIds`. With no polling contract and no hold indicator, this looks like a broken app rather than a busy show. The 409 body already names the seats, so the fix is UI-side — but it needs a plan, not a discovery in week 5.

### 9. `GET /api/bookings` returns every booking a user has ever made
`booking-service/.../controller/BookingController.java:327`, `service/BookingService.java:440-446`, `repository/BookingRepository.java:17`

No `Pageable`, no limit, and the list includes PENDING, CANCELLED and EXPIRED. Every abandoned hold adds a row. event-service's list endpoint is paged and capped at 100 (`EventController`, `spring.data.web.pageable.max-page-size`); this one isn't. A demo account that has been used for load testing will return thousands of rows.

## Tier 4 — untidy, worth logging not fixing now

### 10. Refresh-token reuse is rejected but not treated as theft
`auth-service/.../service/AuthService.java:88-95`. Presenting an already-revoked refresh token returns 401 and stops there. The standard rotation-detection response is to revoke the whole family for that user, because a revoked token being presented means either a replay or a stolen token racing the legitimate client. Here the attacker's *first* use of a stolen token still succeeds and rotates; only the real user's next refresh fails, and they're logged out with no signal that anything happened.

### 11. A crash between the Redis hold and the commit leaks holds for a booking that never existed
`booking-service/.../service/BookingService.java:154-166`. `holdSeats` runs after `save()` but before commit. If the commit fails, the keys survive for the full 10-minute TTL owned by a rolled-back booking id, so those seats are unbookable by anyone. Bounded and already documented in the class javadoc; noting it only for completeness against the "process dies between two steps" brief.

### 12. The expiry sweep full-scans `bookings` every 60 seconds
`booking-service/.../repository/BookingRepository.java:81`, `scheduler/ExpiredBookingSweeper.java:65`. No index on `(status, expires_at)`, declined in a comment as "cheap at this scale". True today. Since `bookings` and `booking_seats` rows are written on every hold and never deleted — including for holds that expired or were cancelled, which the V2 migration comment confirms is intentional — the table that this scans grows monotonically with abandoned checkouts. It's the same shape as the outbox gap, on the table with the highest write rate.

## Where I found nothing

**A double sale.** I walked hold → confirm → cancel → expire, including process death between each pair of steps, and could not construct a sequence where two bookings end up CONFIRMED for one seat. The three layers compose correctly and the reasoning holds up:

- `hold_seats.lua` is genuinely atomic and its rollback is invisible outside the script; `release_seats.lua` is a correct compare-and-delete with string comparison.
- `Booking.confirm()` writes the status flip and `sold_show_seat_id` in one change, and `bookingRepository.flush()` at line 238 runs *before* the event-service call, so the unique index fires before `event_db` is touched. That ordering is load-bearing and it is right.
- `InternalSeatService.markBooked` writes through managed entities, so `@Version` actually engages; the AVAILABLE guard is a fast path and the version is the race-closer, exactly as the comment claims.
- `expiresAt` is always computed before the Redis `SET`, so the Redis TTL always outlives the row's own expiry — the safe direction. Confirm's expiry check therefore rejects a lapsed booking before Redis would.
- Cancel's decision not to check `expiresAt` is safe precisely because the release is value-matched.

The failure mode in this design is not double-selling. It is orphaning (#1) and silent non-confirmation (#2).

**Authorization split across a fetch.** I looked for the pattern specifically. `requireOwner` (BookingService.java:378-397) is the single decision point for confirm, cancel and both reads, it is applied to the locked row itself rather than to an id checked earlier, and "not yours" and "doesn't exist" produce a byte-identical 404. `findByIdOptional` is the one unchecked read and its only caller checks ownership itself. `ShowSeatRepository`'s two lookups are both scoped by `showId` as well as the id list, so ids from another show can't be reached by guessing. No IDOR found.

**Error-response shape drift.** All four services emit `{timestamp, status, error, message, path}` with an `Instant` timestamp, including the gateway's filter-written 401/429 and its own 404 (`GatewayErrorAttributes`). `SeatConflictResponse` adds `conflictingSeatIds` to that shape rather than replacing it, so a generic client parser works on it. No endpoint returns 200 with an error body. This is in better shape than most projects at this stage.

**CORS.** `globalcors` is configured once at the gateway and nowhere else, it covers every browser-facing path, and because Spring Cloud Gateway processes CORS in the handler mapping — before global filters run — the `Access-Control-Allow-Origin` header is present on the 401s and 429s that `RateLimitFilter` and `JwtAuthenticationFilter` write themselves. `Idempotency-Key` is allowed inbound and `Location`, `Retry-After` and `X-RateLimit-Remaining` are exposed. Nothing to fix.

**Redis key growth.** Every namespace has a TTL: `seat:hold:*` (600s), `idem:*` (24h), `notif:dedupe:*` (24h), `ratelimit:token-bucket:*` (`EXPIRE` inside the Lua at TokenBucketRateLimiter.java:109). Nothing unbounded on that side.

---

One thing to note about #1 and #5: both are load-path failures with no test behind them. The k6 suite contends on `/hold` only, and the smoke test runs one confirm at a time against a warm, local event-service. If you want evidence before triaging, the cheapest experiment is to add an artificial 6-second sleep to `InternalSeatService.markBooked`, run a single confirm through the gateway, and then query `event_db.show_seats` and `booking_db.bookings` for that seat — I'd expect `BOOKED` against a `PENDING` booking. I have not run it, so that is a prediction, not a result.
